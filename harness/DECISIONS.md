## 2026-07-24 — Ужесточение прод-инфраструктуры Keycloak/портов
- Решение: Keycloak переведён в боевой режим (`start` вместо `start-dev`; hostname/proxy-переменные уже были корректны — лог `Proxied: true`); публикация портов keycloak/backend/frontend убрана из compose (снаружи только Traefik по HTTPS); `sslRequired: "external"` в prod-realm (Keycloak сам требует HTTPS для внешних запросов — защита в глубину). Каждый шаг — отдельный деплой с проверкой входа; порт Keycloak убрали первым как «канарейку» проверки маршрутизации.
- Почему: закрыть оставшиеся пункты чек-листа перед публичным доступом; прямой доступ по `http://IP:порт` в обход HTTPS — лишняя дверь. Миграции вместо `db push` — отложены отдельной задачей.
- Затронуто: docker-compose.yml, keycloak/realm-export.prod.json, DEPLOY.md

## 2026-07-23 — Второй заход безопасности: realm dev/prod, IDOR, валидация
- Решение: демо-юзеры Keycloak разнесены на dev/prod — `realm-export.prod.json` без секции `users` (прод-compose монтирует его), демо-учётки (`admin1`/`hr1`/…) остаются только в `realm-export.json` для локалки; первого прод-админа заводят вручную. IDOR закрыт проверкой владельца: сотрудник видит/правит только своё (обращения, профиль), HR/admin — всё; автор обращения/комментария из токена, записи опыта/образования скоуплены по employeeId. Валидация: глобальный ValidationPipe + class-validator на DTO обращений, кламп `limit ≤ 100`, белый список полей сортировки.
- Почему: три пункта из «не закрытого» перед VPS; фронт уже показывал сотруднику только своё — серверная проверка закрепила это. Keycloak prod-режим/порты не брали — остаются в чек-листе.
- Затронуто: keycloak/realm-export.prod.json, docker-compose.yml, backend main.ts, appeals/*, profile/*, employees.service.ts, frontend appeals-вызовы, DEPLOY.md

## 2026-07-23 — Базовая безопасность перед выкладкой на VPS
- Решение: rate limit по IP (`@nestjs/throttler`: глобально 120/мин + жёсткий 10/мин на LLM-генерацию и тест LLM), `trust proxy` для реального IP за Traefik, `helmet`, CORS по `FRONTEND_ORIGIN` (вместо `*`). Защита от двойной генерации — серверный замок (`Set` по subjectId → 409), а не клиентский idempotency-key (избыточен). Закрыт анонимный доступ: `KeycloakAuthGuard.handleRequest` бросает 401, `/me` берёт роль из токена (убран `?role=`), guard на appeals/profile/employees. Инфра-риски (демо-юзеры Keycloak, dev-режим, порты, миграции) — чек-лист в DEPLOY.md.
- Почему: перед публичным доступом аудит нашёл дыры опаснее запрошенных 3 понятий; rate limit без закрытия анонимного доступа бессмыслен. Idempotency-key избыточен — хватает серверного замка.
- Затронуто: backend main.ts, app.module.ts, auth/auth.guard.ts, me/*, profile/employees/appeals controllers, report.service.ts, settings.controller.ts, DEPLOY.md

## 2026-07-23 — Отбор сильных сторон/зон развития по методике v1.2, целевой уровень — константа 3,0
- Решение: сильные стороны — компетенции с итоговой (средней, включая самооценку) строго > 3,4 (по убыванию), зоны развития — строго < 3,0 (по возрастанию), 3,0–3,4 — никуда; топ-3 отменён, количество не ограничено; |Δ| ≥ 0,6 — по-прежнему только слепые/скрытые. Целевой уровень — константа методики 3,0: сохранённые значения циклов игнорируются, поле удалено из редактирования цикла (колонка target_level в БД остаётся, не читается). Подзаголовки разделов — «по итогу средней оценки».
- Почему: методика v1.2 задаёт абсолютные пороги от итоговой средней вместо относительного топ-3 и настраиваемого целевого уровня; уровень зашит в методике — настройка лишняя. Неравенства строгие — по формулировкам v1.2 («больше 3,4», «меньше 3,0»).
- Затронуто: analytics.ts (DEV/STRONG_THRESHOLD, selection.strengths), results.service.ts, report.prompt.ts, [cycleId]/page.tsx, Report360View.tsx, reportDocx.ts

## 2026-07-23 — Разделы отчёта взаимоисключающие: |Δ| ≥ 0,6 — только слепые/скрытые
- Решение: компетенции с |Δ| ≥ 0,6 попадают только в blindSpots/hiddenPotential; сильные стороны (топ-3 по окружению) и зоны развития (ниже целевого) отбираются среди компетенций с |Δ| < 0,6 (зона внимания 0,4–0,5 допускается); опустевший раздел объясняется абзацем emptyReasons.
- Почему: у Седлецкого «Системное мышление» дублировалось в сильных сторонах и скрытых возможностях, «Проактивность» — в развитии и скрытых; правила взаимоисключения не было ни в коде, ни в промпте, ни в методике.
- Затронуто: analytics.ts (selection: eligible), report.prompt.ts (техчасть + методика)

## 2026-07-21 — Целевой уровень убран из формы запуска цикла (дефолт 3.0)

## 2026-07-21 — Части генерации последовательно + повтор при 429 (перерешение)
- Решение: части отчёта выполняются последовательно (Promise.all → for-цикл); при 429 «too many concurrent requests» — пауза 15с и 1 повтор; nginx proxy_read_timeout 1300s (2 части × 2 попытки × 300с + запас), Traefik ≥ 1300s; «3 запроса» в редчайшем худшем случае может не уложиться — принято.
- Почему: параллельный запуск (решение того же дня) упёрся в лимит Gonka — одновременные запросы по одному ключу запрещены; 429 возможен и при одновременной генерации двумя HR.
- Затронуто: report.service.ts, llm.client.ts, /admin/llm (подписи), nginx.conf, DEPLOY.md

## 2026-07-21 — Генерация отчёта по частям (splitParts в пресете LLM)
- Решение: число запросов генерации — настройка пресета (1 — одним, дефолт; 2 — разделы / пары+рекомендации; 3 — разделы / пары / рекомендации); части идут параллельно (Promise.all), system каждой части содержит схему только её разделов, код склеивает ответы (из каждой части — только её ключи) через normalizeSections; ошибка любой части = ошибка всей генерации.
- Почему: полный отчёт (~15К токенов) упирается в потолок вывода Gonka 16384, у reasoning-моделей размышления едят тот же бюджет; у каждой части — свой лимит 16384. Параллельно — чтобы уложиться в nginx 700s (последовательно 4×300с не влезает).
- Затронуто: schema.prisma (split_parts), llm.config.ts, report.prompt.ts (TECHNICAL_RULES + фрагменты схемы + partsForCount), report.service.ts, settings.service.ts, /admin/llm

## 2026-07-21 — Автоповтор LLM при таймауте, лимит токенов по галочке, nginx 700s
- Решение: 1 автоповтор запроса к LLM — только при таймауте (не при ошибках разбора/HTTP); max_tokens по умолчанию НЕ отправляется (размер решает провайдер), в пресете — галочка «Ограничить размер ответа» с числовым полем; nginx proxy_read_timeout 700s (2 попытки × 300с + генерация + запас), Traefik на проде — вручную ≥ 700s.
- Почему: лог доказал «лотерею нод» Gonka — первый запрос завис (таймаут 300с), повтор того же промпта прошёл за 84с; явный лимит нужен лишь провайдерам с малым дефолтом.
- Затронуто: llm.client.ts, llm.config.ts, /admin/llm (page.tsx), nginx.conf, DEPLOY.md

## 2026-07-20 — Четвёртая зона «Внимание» (|Δ| 0,4–0,5) в отчёте и таблице
- Решение: все зоны считает одна функция zoneOfDelta по |Δ|, округлённому до 0,1 (единая сетка с категориями): ≤0,3 консенсус; 0,4–0,5 внимание; ≥0,6 слепая/скрытая по знаку. В разборах пар — четвёртая группа «Зона внимания», в таблице результатов — жёлтая пилюля «Внимание»; в промпте — легенда русских названий категорий (модель не называет категорию своими словами).
- Почему: по методике консенсус — строго ≤0,3, а 0,4–0,5 попадали под «оценки близки»; дискретная сетка категорий (0,2–0,3; 0,4–0,5…) подразумевает округление до 0,1; одна функция исключает расхождение таблицы и отчёта.
- Затронуто: analytics.ts, results.service.ts, report.types.ts, report.prompt.ts, api.ts, helpers.ts, Report360View.tsx

## 2026-07-20 — Зоны и составы разделов отчёта считает код, LLM пишет только тексты
- Решение: классификация зон (zoneOfDelta: знак Δ, порог 0,6 нестрого) и отбор разделов (selection: топ-3 сильных по окружению, зоны развития ниже целевого, слепые/скрытые по знаку Δ) — детерминированно в analytics.ts; техчасть промпта запрещает модели переклассификацию/пересчёт; пустые разделы модель объясняет абзацем (emptyReasons).

## 2026-07-19 — Конвенции усреднения подтверждены аудитом

## 2026-07-19 — Правило «генерация только по-русски» в технической части промпта

## 2026-07-17 — Два якоря сброса отчёта: initialSnapshot + preGenSnapshot
- Решение: два снимка в Cycle360Report — `initialSnapshot` (фиксируется один раз, до первой генерации) и `preGenSnapshot` (перед каждой генерацией); при откате снимки не обнуляются.
- Почему: HR нужен выбор «до всех генераций» / «на шаг назад»; неснимаемые якоря позволяют переключаться между ними до следующей генерации. Полная история версий отвергнута — шире скоуп без запроса.
- Затронуто: schema.prisma (2 nullable Json), report.service.ts (reset(mode)), ReportView.tsx (модалка с двумя действиями)

## 2026-07-17 — Таймауты генерации: LLM-клиент 300с, nginx /api 330с
- Решение: поднять таймаут запроса к LLM до 300с, а `proxy_read_timeout` nginx до 330с (строго больше backend).
- Почему: reasoning-модель MiniMax не укладывалась в 120с; прокси должен рвать соединение позже backend, иначе ошибка маскируется.
- Затронуто: llm.client.ts, nginx/nginx.conf, DEPLOY.md (в т.ч. напоминание про Traefik)

## 2026-07-17 — Пилотный LLM-провайдер: Gonka/OpenGNK, модель MiniMax-M2.7
- Решение: для автогенерации использовать proxy.gonka.gg (OpenAI-совместимый прокси децентрализованной сети Gonka), модель `MiniMaxAI/MiniMax-M2.7`.
- Почему: почти бесплатно (~$0.00015/1M токенов + 1M бесплатных), протокол 1-в-1 совпадает с нашим клиентом — подключение без правок кода; Kimi/GLM из доки фактически недоступны (404).
- Затронуто: только настройки /admin/llm (base URL https://api.proxy.gonka.gg/v1)

## 2026-07-16 — Отказ от OAuth-токена подписки Claude для автогенерации
- Решение: не использовать OAuth-токен подписки Pro/Max как источник LLM для портала; легальный путь — API-ключ (Console) + OpenAI-совместимый прокси (LiteLLM) либо иной провайдер.
- Почему: токен подписки предназначен для интерактивной личной работы — использование в приложении против условий; технически короткоживущий, не обновляется автоматически.
- Затронуто: архитектура подключения LLM (кода не потребовалось)

## 2026-07-16 — Настройки LLM в БД с приоритетом над env
