## 2026-08-31 — «Показывает 5 вместо 6» — не лимит вывода, а потеря ввода
- Что случилось: 6-й индикатор шаблона 360 «пропадал после сохранения»;
  искали лимит отображения — его в коде нет вовсе.
- Причина: в форме с автосохраняемыми полями одно поле требовало явной кнопки
  «Добавить» — набранный текст молча пропадал при «Готово». Попутно: гейт
  `if (loading) return «Загрузка...»` на каждой перезагрузке размонтировал
  инпуты и убивал несохранённый текст в них.
- Урок: симптом «данные пропали» проверять сперва на пути ввода, потом вывода;
  фоновые reload не должны включать полноэкранный лоадер.

## 2026-08-07 — Вставленные блоком prisma-команды выполнились не все
- Что случилось: после миграции «минимум полей» локально падало создание
  сотрудника (Null constraint violation: position_id). Обе команды миграции
  вставлялись в cmd одним блоком — выполнился только `prisma generate`,
  а строка `prisma db push` вклеилась в его вывод и не запустилась.
- Причина: диагноз поставлен по логу — в нём нет ни строки вывода db push
  (нет «database is now in sync»), схема БД осталась старой (NOT NULL).
- Урок: команды миграции запускать по одной и проверять по характерному
  выводу успеха, а не по отсутствию ошибок; «выполнил команды» ≠ «команды
  выполнились».

## 2026-07-30 — Сид ставил второй default-флаг шкале

  местах записи — включая сиды и разовые скрипты, а не только в основном сервисе.

## 2026-07-28 — Локальная генерация падала «fetch failed»: провайдер блокирует LLM-прокси, нужен VPN
- Что случилось: на локальном бэкенде генерация отчёта падала через ~20 с с «LLM недоступен:
  fetch failed». С прод-сервера `curl` к `api.proxy.gonka.gg` отвечал (сервис жив), с локальной
  машины — нет; с включённым VPN генерация прошла.
- Причина: домашний провайдер блокирует адрес LLM-прокси. Диагноз затянулся, потому что
  Node-fetch прячет настоящую причину: в лог уходит только «fetch failed», а ENOTFOUND/
  ETIMEDOUT лежит в `e.cause` (в лог не выводится — отдельная мелкая правка llm.client.ts).
- Урок: «fetch failed» = сеть до провайдера, а не сам провайдер — сравнивать доступность
  с двух точек (локально и с прод-сервера), прежде чем винить сервис. Для локальной
  разработки с LLM держать VPN включённым. При этом днём раньше тот же VPN ломал
  диагностику сервера (резал 22/443 при живом сайте) — VPN влияет в обе стороны:
  в любой сетевой загадке первым делом проверять его состояние и пробовать оба варианта.

## 2026-07-28 — Удаление «проекта» в панели хостера унесло боевой сервер
- Что случилось: при чистке ненужного проекта в Timeweb удалился сервер портала (он
  назывался `Orgchart_server` и не читался как прод). Сутки простоя. Диагностику дважды
  уводили в сторону: старый IP из dev-realm (по нему искали «живой» сервер) и 503 от
  балансировщика, который отвечал вместо удалённой машины.
- Причина/ход: сервер нашёлся в разделе «Удалённые» и восстановился с диском, но получил
  новый IP и потерял приватную сеть (eth1 пришлось поднимать руками через netplan);
  балансировщик после этого сломался на стороне хостера (в его конфиге адрес сервера
  записался как его собственный) — выведен из цепочки: домен направлен напрямую на
  сервер, TLS выпущен на Traefik (Let's Encrypt). Данные не пострадали.
- Урок: боевые ресурсы называть по назначению (`hr-portal-prod`) и держать автобэкапы;
  диагностику начинать с панели хостера (статус машины, её ТЕКУЩИЙ IP), а не с ping по
  адресу из памяти; балансировщик перед единственным сервером — лишняя точка отказа;
  серверные IP в репозитории не хранить — устаревают и сбивают диагностику.

## 2026-07-27 — Потолок вывода определяет брокер, а не модель и не сеть
- Что случилось: на GonkaRouter обе модели обрывались ровно на 4096 при запрошенных 8192,
  а без явного `max_tokens` — на 3072. Отчёт пришлось дробить с 3 частей до 8, и он всё
  равно собирался не для всех сотрудников: по одному собрался, по другому нет.
- Причина: та же модель через `api.proxy.gonka.gg` даёт 16384 — ограничение накладывает
  посредник. Дефолт шлюза (3072) ниже его же потолка (4096). За шлюзом Cloudflare со своим
  таймаутом ~2 мин: долгая генерация приходит HTML-страницей 524, а не ошибкой API.
- Урок: потолок и дефолт узнавать замером (`completion` при `finish_reason=length`), а не
  по документации; дешёвый брокер может стоить дороже в разработке, чем экономит на токенах.

## 2026-07-27 — Запрошенный max_tokens не поднимает потолок шлюза
- Что случилось: на GonkaRouter генерация обрывалась на середине JSON; в логе
  `finish_reason=length, completion=4096` при `запрошенный max_tokens=8192` — и у
  MiniMaxAI/MiniMax-M2.7, и у moonshotai/Kimi-K2.6.
- Причина: потолок вывода принадлежит шлюзу, а не модели и не нашему запросу;
  документация router.mingles.ai для того же Kimi заявляет 8192 — на этом шлюзе не действует.
- Урок: реальный потолок узнавать по `completion` при `finish_reason=length` на боевом
  прогоне, а не из документации. Модели одного шлюза упираются в него на разных частях
  (Kimi пишет длиннее и без `<think>`) — число частей подбирать по худшей из них.

## 2026-07-24 — 502 при долгой генерации давал прокси, а не бэкенд
- Что случилось: на «AI генерация отчёта» приходил 502 через ~10–15 с, кнопка снова активна, но отчёт «в итоге появлялся». Грешили на таймаут Traefik и правили его — не помогло.
- Причина (доказательство — лог backend): все LLM-вызовы успешны (`finish_reason=stop`, ~3 мин), строк-ошибок LLM нет вообще → 502 отдаёт не бэкенд, а прокси, обрывая долго висящий HTTP-запрос; бэкенд генерацию доводит до конца.
- Урок: диагноз брать из лога сервиса, а не из предположения о прокси. UI долгих операций не должен зависеть от живого HTTP-запроса — переживать обрыв опросом результата (Вариант A) или асинхронным статусом на сервере (Вариант B). «Мгновенная повторная генерация» = кэш провайдера (Gonka), не наш код.

## 2026-07-24 — Закрывать порты за прокси — «канарейкой», а не разом
- Что случилось: перед удалением `ports:` у трёх сервисов было неизвестно, как Traefik/Dokploy доходит до контейнеров — по внутренней docker-сети или через опубликованные хост-порты (Traefik-меток в compose нет, маршрутизация в самом Dokploy).
- Причина: удаление всех портов сразу при маршрутизации через хост-порт положило бы весь сайт разом, без понимания причины.
- Урок: убирать по одному — сначала один некритичный сервис (Keycloak), деплой, проверка входа по домену; если работает и прямой порт закрыт — Traefik ходит по сети, остальные порты безопасно. Тот же принцип для любой рискованной инфра-правки без видимого конфига прокси.

## 2026-07-23 — forbidNonWhitelisted ломает клиентов, шлющих лишние поля
- Что случилось: включили глобальный ValidationPipe с `forbidNonWhitelisted` и перевели DTO обращений в классы; фронт продолжал слать `authorId` в теле — такой запрос стал падать в 400 (лишнее поле), хотя по смыслу валиден.
- Причина: `forbidNonWhitelisted` отклоняет любые поля, не описанные декораторами DTO; поле `authorId` теперь ставится из токена и в теле лишнее.
- Урок: при переводе DTO в валидируемые классы синхронно чистить клиентские вызовы (убрать поля, которые сервер теперь берёт из токена/контекста). ValidationPipe с `whitelist` действует только на DTO-классы; для DTO-интерфейсов это no-op — включать построчно по мере перевода.

## 2026-07-23 — Сломанный guard обесценивал авторизацию (null вместо 401)
- Что случилось: аудит перед деплоем нашёл, что `KeycloakAuthGuard.handleRequest` возвращал `null` вместо исключения — эндпоинты под этим guard без `@Roles` были доступны без токена; `/me?role=admin` без токена отдавал admin-заглушку.
- Причина: у passport-`AuthGuard` `handleRequest` при `!user` ДОЛЖЕН бросать `UnauthorizedException`; возврат `null` тихо пропускает запрос с `req.user=null`, и защищает только `RolesGuard` (а он есть не везде).
- Урок: при наследовании passport `AuthGuard` всегда проверять, что `handleRequest` бросает исключение, а не возвращает null/undefined. Роль пользователя брать только из токена, не из query/тела (иначе impersonation).

## 2026-07-23 — Формат файла базы знаний не влияет на расход токенов
- Что случилось: проверяли гипотезу «методики в .md тратят меньше токенов, чем .docx» — конвертация показала, что md даже чуть больше (+1–4%): docx и так превращается в чистый текст при загрузке, а разметка md добавляет символы.
- Причина: в промпт идёт извлечённый текст, формат исходного файла роли не играет; экономит только сокращение самого текста.
- Урок: для экономии токенов — сокращать документы (выжимки вместо полных текстов), а md использовать ради явной структуры (заголовки/списки помогают модели ориентироваться), не ради токенов.

## 2026-07-21 — У Gonka лимит одновременных запросов по одному ключу
- Что случилось: параллельный запуск двух частей генерации мгновенно дал HTTP 429 «rate limit exceeded: too many concurrent requests» — обе части столкнулись через секунду.
- Причина: провайдер ограничивает число одновременных запросов по API-ключу (фактически 1).
- Урок: оркестрацию LLM-запросов проектировать последовательной по умолчанию; параллель — только после проверки лимитов конкретного провайдера. Таймаут прокси пересчитывать при каждом изменении схемы попыток (число частей × попытки × таймаут клиента + запас).

## 2026-07-21 — Зависшая нода децентрализованного провайдера лечится повтором, а не таймаутом
- Что случилось: генерация упала по таймауту 300с, а повтор того же запроса через полминуты прошёл за 84 секунды — идентичные запросы к Gonka отличаются по времени в разы (какая нода попадётся).
- Причина: децентрализованная сеть — запросы маршрутизируются на разные ноды, часть медленные/зависшие.
- Урок: при таймауте сначала повторить запрос (второй шанс на живую ноду), а не наращивать таймаут одной попытки; таймаут reverse-proxy считать как таймаут клиента × число попыток + запас; лог размера промпта до запроса и usage после — обязательны, иначе такие случаи не диагностируются.

## 2026-07-21 — NestJS отдаёт return null как 200 с пустым телом
- Что случилось: сброс отчёта без снимков (сервис возвращает null после удаления) давал на фронте «Unexpected end of JSON input» — res.json() на пустом теле; прерванный обработчик не перечитал состояние, и устаревший текст висел в UI до перезагрузки страницы.
- Причина: fetchApi обрабатывал только статус 204, а NestJS сериализует null как 200 без тела.
- Урок: тело ответа читать через text() с проверкой на пустоту, а не res.json(); перечитку состояния после мутирующих запросов класть в finally — сервер мог выполнить операцию даже при ошибке чтения ответа.

## 2026-07-20 — Math.round в JS несимметричен для отрицательных чисел
- Что случилось: при переводе зон на сетку 0,1 прямое округление Δ дало бы −0,55 → −0,5 («внимание»), тогда как +0,55 → +0,6 (слепая зона) — граница работала бы по-разному для слепых зон и скрытого потенциала.
- Причина: Math.round округляет половинки к +∞ (Math.round(-5.5) = -5, Math.round(5.5) = 6).
- Урок: при классификации по знаку и модулю округлять |Δ| и восстанавливать знак; граничные случаи (±0,55) обязательно включать в смоук.

## 2026-07-20 — Reasoning-модель может сжечь весь max_tokens на <think> и не выдать JSON
- Что случилось: генерация падала с «Модель вернула только рассуждения без JSON» — модель потратила все 16000 токенов на размышления (заново анализировала данные), не начав ответ.
- Причина: длина размышлений случайна от запуска к запуску и растёт от строгих правил в промпте (после задачи №38 модель «думала» дольше); лимит 16000 упирался в потолок Gonka 16384.
- Урок: у reasoning-моделей бюджет вывода ставить в потолок провайдера и прямо указывать «рассуждай кратко, все решения уже приняты системой, сразу переходи к JSON»; лимит держать настраиваемым — потолки у провайдеров разные.

## 2026-07-20 — LLM нельзя доверять классификацию и арифметику даже на готовых числах
- Что случилось: в отчёте Седлецкого модель положила скрытые возможности (Δ до −2,9) в «Слепые зоны», пропустила компетенции в разборах пар, не включила лучшую компетенцию (окружение 4,25) в сильные стороны и написала «3,17 ниже 3,0» — при том, что все числа ей передавались готовыми и верными.
- Причина: модель выполняла классификацию/отбор сама по текстовым правилам промпта и ошибалась в знаке Δ и критериях.
- Урок: всё детерминированное (пороги, знаки, сортировки, составы списков) считать кодом и передавать готовыми метками; модели оставлять только интерпретационный текст; проверять её выводы против собственных цифр отчёта.

## 2026-07-19 — Ошибка гидрации Next.js из-за localStorage в первом рендере
- Что случилось: «Text content does not match server-rendered HTML» при открытии портала — сервер и клиент рендерили разные меню Sidebar.
- Причина: AuthContext читал localStorage (сохранённая роль) в инициализаторе useState — на сервере localStorage нет, на клиенте роль другая.
- Урок: браузерное состояние (localStorage/время/random) применять только в useEffect после монтирования; предупреждение в консоли («Prop d did not match» + стек) точно указывает компонент-виновник.

## 2026-07-19 — Границы категорий держать в одном месте
- Что случилось: порог слепой зоны 0,6 в таблице (строгое >) и в промпте («0,6 и более») разошёлся — разрыв ровно 0,60 классифицировался по-разному в таблице и в тексте ИИ.
- Причина: одно и то же правило методики закодировано в двух местах разными сравнениями.
- Урок: пороговые сравнения считать на округлённых значениях и нестрого (>=); формулировки промпта сверять с кодом при каждой правке порогов.

## 2026-07-17 — Reasoning-модель кладёт <think> прямо в content
- Что случилось: генерация падала «в ответе нет JSON» — ответ MiniMax начинался с `<think>…</think>`, а внутри рассуждений были фигурные скобки, ломавшие разбор «от первой { до последней }».
- Причина: reasoning-модели вкладывают рассуждения в `content` (или в отдельное поле `reasoning_content`); наш парсер этого не ожидал.
- Урок: перед извлечением JSON срезать `<think>…</think>` (и висячий незакрытый `<think>`); проверять `reasoning_content` как запасной источник; ставить явный `max_tokens`, чтобы рассуждения не съедали бюджет ответа.

## 2026-07-17 — PowerShell ломает UTF-8 кириллицу в теле запроса
- Что случилось: при ручной проверке API через `Invoke-RestMethod` в модель ушли «?????» вместо русского текста — модель отвечала не на тот вопрос и по-китайски.

## 2026-07-17 — Таймаут reverse-proxy должен быть больше таймаута backend→LLM
- Что случилось: генерация обрывалась «таймаут запроса», хотя модель ещё работала.
- Причина: сначала мал был таймаут LLM-клиента (120с), при подъёме — nginx (180с) резал бы раньше backend (300с).
- Урок: таймауты в цепочке браузер→nginx→backend→LLM поднимать согласованно; прокси всегда с запасом больше backend (у нас 330с против 300с).

## 2026-07-16 — Список моделей провайдера брать только из GET /v1/models
- Что случилось: `moonshotai/Kimi-K2.6` из документации Gonka дал 404 model_not_found; реально сервер отдавал одну `MiniMaxAI/MiniMax-M2.7`.

## 2026-07-16 — Правка schema.prisma = всегда ПАРА: generate + db push
- Что случилось: дважды ловили ошибки по отдельности — TS2339 «Property 'llmSettings' does not exist on PrismaService» и «The table … does not exist in the current database».
- Причина: `prisma generate` обновляет только типы клиента, `prisma db push` — только структуру БД; по одной команде получается половина результата.
- Урок: после любого изменения схемы выполнять обе: `node_modules\.bin\prisma generate` и `node_modules\.bin\prisma db push`, затем перезапуск backend.

## 2026-07-16 — Глобальный npx prisma тянет Prisma 7 и падает
- Что случилось: `npx prisma …` завершался ошибкой P1012 на валидной схеме.
- Причина: глобальный npx ставит свежую Prisma 7, проект — на Prisma 6.

## 2026-07-15 — git pull падает на изменённом package-lock.json
- Что случилось: `git pull origin mvp2` отказывался: «Your local changes to backend/package-lock.json would be overwritten».
- Причина: локальная сборка меняет lockfile, изменения не закоммичены.
- Урок: `git checkout -- backend/package-lock.json`, затем pull; lockfile локально не править.
