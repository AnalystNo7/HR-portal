# PLAN: Минимальный набор полей сотрудника + подтверждение при пропусках

BRIEF: tasks/optional-fields/BRIEF.md (создан, чек-лист выхода пройден).
Решения человека: минимум = табельный + фамилия + имя + email; пустые
должность/подразделение — честный NULL (миграция); импорт не затирает
базу пустыми полями; подсказка — модальное окно и в импорте, и в форме.

## Контекст

Сейчас сотрудника нельзя завести без 5 полей: импорт молча отбрасывает
строки без должности/подразделения (import.service.ts:96-105, :140),
ручная форма падает на сервере (Prisma NOT NULL). Нужен минимум из четырёх
полей и явное подтверждение «не заполнено — продолжить?» вместо молчаливых
пропусков. Заодно закрывается открытый вопрос UR-008 (строки без email).

## Шаги

1. **Схема** — `backend/prisma/schema.prisma`: `positionId`/`departmentId`
   (+ relations) → nullable (`String?`). Аддитивно (ослабление NOT NULL,
   данные не теряются, CON-003 соблюдён).

2. **Импорт, бэкенд** — `import.service.ts`:
   - `ParsedRow` + поле `warnings: string[]`; в parseExcel жёсткие errors
     только для минимума (табельный, фамилия, имя, email); пропуски
     должности/подразделения → warnings.
   - executeImport: валидны строки без errors (warnings импортируются);
     в upsert-update опциональные поля подставлять только если непустые
     (пустое в файле не затирает базу — `...(row.position ? {positionId} : {})`);
     в create — NULL при пустых.
   - В ImportResult добавить сводку warnings для окна подтверждения.

3. **Импорт, фронт** — `frontend/app/admin/import/page.tsx`:
   - строки с warnings в предпросмотре помечать жёлтым (не красным);
   - кнопка «Импортировать» при наличии warnings открывает Modal со сводкой
     «В N строках не заполнено: должность (X), подразделение (Y)… Эти поля
     останутся пустыми. Продолжить?» → «Продолжить» / «Отмена». Компонент
     Modal переиспользуется (как в ReportView).

4. **Ручная форма** — `frontend/app/admin/employees/page.tsx`:
   - обязательные поля (табельный, фамилия, имя, email) помечены `*`,
     без них «Сохранить» показывает ошибку;
   - при пустых опциональных — Modal «Не заполнены: должность, … —
     Продолжить?»; селекты должности/подразделения получают пункт «—»;
   - dto: пустые positionId/departmentId не отправляются.

5. **Сервер, создание/правка** — `employees.controller.ts` + service:
   `positionId`/`departmentId` в DTO опциональны; серверная проверка
   минимума (400 при пустых табельном/фамилии/имени/email — не полагаясь
   на UI, NFR-005).

6. **Null-безопасность отображения** — единственное падающее место:
   `cycle.service.ts:62` (`department.name`) → фильтр/`?.` с «—».
   Фронт уже безопасен (`position?.name ?? ''`) — заменить пустышку на «—»
   в списках сотрудников (admin/employees, hr) для видимости пропуска.

7. **Проверки** — смоук parseExcel (строка-минимум → warnings, без
   минимума → errors); tsc/build backend+frontend; коммит и пуш в mvp2.

## Альтернативы (отвергнутые)

- Заглушка «Не указано» вместо миграции: мусорная запись в справочниках
  и фильтрах, «не заполнено» неотличимо от заполненного — отвергнута
  человеком при опросе.
- Валидировать только на фронте без серверной проверки минимума:
  обходится прямым запросом (урок NFR-005) — не устраняет причину.

## Риски

- 🟡 db push на проде ослабляет NOT NULL — операция аддитивная, но идёт
  через CMD контейнера; следим за логом старта backend после деплоя.
- 🟡 Keycloak createKeycloakUsers использует row.firstName/lastName —
  минимум их гарантирует; проверить, что пустые не уходят при апдейте.
- 🟢 Существующие данные не меняются: все текущие сотрудники заполнены.
