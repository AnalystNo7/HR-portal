# PLAN: Опросы → «Выгорание (MBI)»

Дата: 2026-08-17. BRIEF: tasks/burnout-survey/BRIEF.md (чек-лист пройден).

## Шаги

1. **Схема** — schema.prisma, новая таблица (аддитивно):
   `BurnoutResult { id, employeeId→Employee, takenAt, exhaustion Int,
   depersonalization Int, reduction Int, sourceUrl String?,
   source String (MANUAL|IMPORT), createdById String?, createdAt }`,
   `@@map("burnout_results")`, индекс (employeeId, takenAt).

2. **Backend: константы методики** — новый модуль `src/surveys/`
   (module/controller/service + burnout.methodology.ts):
   пороги трёх шкал и формула ИСП из BRIEF — единственная точка правил
   (по образцу analytics.ts); функции `levelOf(scale, value)` и `ispOf()`.

3. **Backend: API** (roles guard как в остальном проекте):
   - `GET /surveys/burnout/my` — свои замеры + вычисленные уровни/ИСП;
   - `POST /surveys/burnout` — сотрудник вносит своё; HR/admin — за
     любого (`employeeId` в dto); серверная валидация диапазонов
     (0–54/0–30/0–48) и даты; владелец проверяется на сервере (NFR-002);
   - `PUT/DELETE /surveys/burnout/:id` — только hr/admin (решение 6);
   - `GET /surveys/burnout` — hr/admin: последние замеры по всем
     с фильтром по подразделению + история сотрудника;
   - `GET /surveys/burnout/team` — manager: подчинённые (managerId),
     ТОЛЬКО уровни трёх шкал и дата, баллы и ИСП не отдаются
     (фильтрация на сервере, не в UI);
   - `POST /surveys/burnout/import/preview|execute` — hr/admin, Excel
     (колонки: employee_number|email, date, exhaustion, depersonalization,
     reduction) — по образцу import.service: errors (сотрудник не найден,
     балл вне диапазона, нет даты), предпросмотр → подтверждение.

4. **Frontend: /surveys** — заменить StubPage на страницу с вкладками
   (первая «Выгорание (MBI)», каркас под будущие опросы):
   - сотрудник: кнопка-ссылка «Пройти тест» (psytests, новая вкладка),
     «Внести результат» (Modal: дата, 3 балла с подсказками диапазонов,
     ссылка опц.), таблица своих замеров — баллы, цветные пилюли уровней
     (палитра scaleBg/pill-*), ИСП;
   - HR: таблица по сотрудникам (последний замер, уровни цветом, ИСП,
     дата), фильтр по подразделению, «Внести за сотрудника», правка/
     удаление, «Загрузить из Excel» (upload → предпросмотр → окно
     подтверждения — паттерн admin/import);
   - руководитель: таблица подчинённых — ФИО + пилюли уровней + дата.
   Видимость режимов — по ролям из токена, как в остальном приложении.

5. **Проверки**: node-смоук методики (ИСП(31,11,21)=0.51; уровни
   31→высокий, 11→высокий, 21→высокое выгорание; границы 15/16, 5/6,
   36/37); tsc/build оба; коммит и пуш в mvp3; блок prisma-команд для
   локальной машины в итоговом сообщении (правило 6).

## Альтернативы (отвергнутые)

- Хранить уровни и ИСП в БД: дублирование производных данных — при
  уточнении порогов пришлось бы мигрировать данные; вычисление кодом
  из сырых баллов бесплатно и всегда согласовано (принцип FR-002).
- Отдавать руководителю полные замеры и прятать баллы в UI: обходится
  прямым запросом (урок NFR-002/IDOR) — фильтрация только на сервере.

## Риски

- 🟡 Достоверность ручного ввода (сотрудник может ошибиться/приукрасить):
  смягчение — опциональная ссылка на результат psytests для сверки HR-ом;
  автопроверку не делаем (решение 1).
