# PLAN: точность интерпретации отчёта 360

Дата: 2026-07-20

## Шаги

1. analytics.ts: zoneVsOthers/zoneByGroup (знак Δ, порог 0,6 нестрого, округлённое значение)
   + selection-списки (strengthsTop топ-3 по окружению, developmentAreas ниже целевого,
   blindSpots/hiddenPotential по zoneVsOthers).
2. report.prompt.ts: в TECHNICAL_PROMPT — блок «классификация выполнена системой» (строго по
   спискам/меткам, все компетенции в парах, цифры не пересчитывать, emptyReasons для пустых);
   схема + emptyReasons; DEFAULT_METHODOLOGY выровнять.
3. report.types.ts + api.ts: emptyReasons в Report360Sections, normalizeSections (причина
   хранится только для пустых разделов).
4. Report360View: показ абзаца-причины при пустом разделе (в т.ч. сотруднику), textarea для
   правки в режиме редактирования.
5. Смоук buildAnalytics на цифрах Седлецкого + смоук сборки промпта; tsc/build; коммит, пуш.

## Альтернативы

- Ужесточение только промпта (без меток в данных): отвергнута — не устраняет причину
  (модель продолжает решать сама и ошибаться в знаке), проверено на реальном отчёте.
- Полностью шаблонные тексты без LLM: отвергнута — теряется ценность индивидуальной
  интерпретации и комментариев, ради которой делалась генерация.

## Риски

- 🟡 Кастомный промт HR в БД противоречит новым правилам («выбери 3–5») → следим: техническая
  часть перекрывает; после деплоя рекомендовать «Сбросить к стандартному».
- 🟡 Модель проигнорирует строгие правила → следим приёмкой на Седлецком; крайний шаг —
  программная пост-валидация составов (следующая итерация).
- 🟢 Рост объёма ответа (все компетенции в парах) — max_tokens 16000 достаточно.
