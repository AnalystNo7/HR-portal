# План: генерация отчёта по частям (1/2/3 запроса, настройка в пресете LLM)

## Контекст

Ответ целиком (~15К токенов) упирается в потолок вывода Gonka 16384, особенно у
reasoning-моделей (размышления едят тот же бюджет). Пользователь хочет MiniMax
(быстрее) и разбивку вывода. Решения: число запросов — выпадающий список в пресете
LLM («Одним запросом / 2 запроса / 3 запроса»), по умолчанию — одним (как сейчас);
части запускаются ПАРАЛЛЕЛЬНО; ошибка любой части = ошибка всей генерации.
Каждая часть получает свой лимит 16384 и думает над меньшей задачей.

## Изменения

### 1. `backend/prisma/schema.prisma`
`LlmSettings.splitParts Int? @map("split_parts")` — null = 1 (одним запросом).
Аддитивно. После правки — prisma generate + db push (правило №6: команды для
Windows cmd в итоговом сообщении).

### 2. `backend/src/oc360/report/llm.config.ts`
- `LlmConfig.splitParts: number` (1|2|3); `LlmSettingsRaw.splitParts: number | null`.
- resolveLlmConfig: значение из БД, кламп в {1,2,3}, дефолт 1; loadLlmSettings читает поле.

### 3. `backend/src/oc360/report/report.prompt.ts` — почастные промпты
- Разрезать TECHNICAL_PROMPT на общие правила (классификация, язык, «рассуждай
  кратко») и блок схемы. Экспортируемый TECHNICAL_PROMPT (полная схема) СОХРАНИТЬ —
  он показывается во вкладке «Технический промт».
- `ReportPart = 'sections' | 'pairs' | 'recommendations' | 'full'` и наборы ключей:
  2 части: [strengths+developmentAreas+blindSpots+hiddenPotential+emptyReasons],
  [groupComparison+recommendations]; 3 части: разделы / groupComparison / recommendations.
- buildSystemPrompt(a, methodology, docs, part='full'): техчасть со схемой только
  нужных ключей + строка «верни ТОЛЬКО перечисленные разделы, остальные не включай».

### 4. `backend/src/oc360/report/report.service.ts` — параллельная сборка
- generate: взять cfg (llm.getConfig()); parts=1 → как сейчас;
  parts=2|3 → Promise.all по частям (одинаковый user-промпт, свой system);
  из ответа каждой части взять ТОЛЬКО её ключи, склеить объект, normalizeSections.
- Ошибка любой части (после автоповтора в клиенте) → вся генерация падает (Promise.all).
- Лог: «LLM: генерация из N частей» перед стартом.

### 5. `backend/src/settings/` + frontend
- splitParts в CRUD пресетов (валидация: целое 1..3, null=1) и в LlmPresetView.
- `frontend/lib/api.ts`: splitParts в LlmPreset/SaveLlmDto.
- `frontend/app/admin/llm/page.tsx`: select «Генерация отчёта»: «Одним запросом
  (стандартно) / 2 запроса (параллельно) / 3 запроса (параллельно)» рядом с лимитом;
  в строке пресета показывать «· 2 запроса», если задано.

### 6. Процесс: `tasks/split-generation/BRIEF.md` + `PLAN.md`.

## Проверка

1. Смоук промптов: system части «sections» содержит только свои ключи схемы и не
   содержит groupComparison; часть «pairs» — наоборот; full = как раньше.
2. Смоук generate со стабом completeJson: parts=2 → два вызова, объединённые
   sections содержат разделы из первой части и пары+рекомендации из второй;
   parts=1 → один вызов; ошибка одной части → генерация падает целиком.
3. Смоук resolveLlmConfig: splitParts null→1, 2→2, 5→кламп 3, 0→кламп 1.
4. tsc оба пакета, next build; prisma generate + db push (локально БД нет — прод
   применит при старте, пользователю — команды по правилу №6).
5. Коммит в mvp2, пуш; записи в журналы.
6. Приёмка: в пресете MiniMax выбрать «2 запроса», перегенерировать — в логе две
   пары строк запрос/usage, отчёт целый; completion каждой части < 16384.

## Отвергнутые альтернативы

- Выбор числа частей в окне генерации у HR: технический выбор ложится на HR при
  каждом запуске; это свойство подключения — место ему в пресете.
- Последовательный запуск частей: худший случай 4×300с > nginx 700с, пришлось бы
  снова поднимать таймауты; параллельный укладывается в текущие.
- Сохранение «готовой половины» при ошибке: сложнее состояние, отвергнуто
  пользователем в пользу «целиком или ничего».
