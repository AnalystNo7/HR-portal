# План: четвёртая зона «Зона внимания» (0,4–0,5) в отчёте и таблице

## Контекст

По методике зона консенсуса — строго |Δ| ≤ 0,3; диапазон 0,4–0,5 — «зона внимания».
Сейчас и отчёт (zoneOfDelta, analytics.ts), и таблица результатов (results.service.ts:125)
относят всё < 0,6 к консенсусу — Проактивность и Решение проблем с Δ 0,5 попали в
«оценки близки». Решения пользователя: вариант 1 (четвёртая зона, считает код);
границы по округлению Δ до 0,1 (единая сетка с категориями); пометка 0,4–0,5 и в
таблице результатов; название «Зона внимания»; перегенерирует отчёты сам.

## Изменения

### 1. `backend/src/oc360/results/analytics.ts`
- `ZoneKind` += `'ATTENTION'`; порог `ATTENTION_EPS = 0.4`.
- `zoneOfDelta`: округлять |Δ| до 0,1 С СОХРАНЕНИЕМ ЗНАКА симметрично
  (`a = Math.round(Math.abs(d)*10)/10`, иначе −0,55 округлится в −0,5 вместо −0,6 —
  JS Math.round несимметричен для отрицательных): a ≥ 0,6 → BLIND/HIDDEN по знаку;
  a ≥ 0,4 → ATTENTION; иначе CONSENSUS.
- selection (слепые/скрытые ≥ 0,6) — логика не меняется, только граница теперь по
  округлению до 0,1 (0,55 → слепая зона), как выбрал пользователь.

### 2. `backend/src/oc360/results/results.service.ts`
Инлайн-расчёт зоны (строки 125–129) заменить на `zoneOfDelta(gap)` из analytics —
таблица и отчёт гарантированно совпадают; тип зоны — ZoneKind.

### 3. `backend/src/oc360/report/report.types.ts`
`DeltaKind` += `'ATTENTION'`; массив KINDS в normalizeSections. Старые отчёты с тремя
kind остаются валидными (изменение аддитивное).

### 4. `backend/src/oc360/report/report.prompt.ts`
- TECHNICAL_PROMPT: сетка зон по |Δ|, округлённому до 0,1: ≤0,3 CONSENSUS; 0,4–0,5
  ATTENTION; ≥0,6 BLIND_SPOT/HIDDEN_POTENTIAL по знаку; kind строго из zoneByGroup.
  В схеме enum kind: CONSENSUS|ATTENTION|BLIND_SPOT|HIDDEN_POTENTIAL.
- Туда же — легенда категорий расхождений русскими словами (0,0–0,1 «практически
  полное совпадение» … >1,2 «критический разрыв») + правило называть категорию
  строго по сетке: закрывает замеченную пользователем ошибку «системное расхождение»
  при Δ = 1,5 (должно быть «критический разрыв»).
- DEFAULT_METHODOLOGY: консенсус ≤ 0,3, зона внимания 0,4–0,5 (вместо «не больше 0,3 …»).

### 5. Frontend
- `lib/api.ts`: `EvalZone` и `DeltaKind` += `'ATTENTION'`.
- `components/eval360/helpers.ts`: ZONE_LABEL.ATTENTION = 'Внимание',
  ZONE_PILL.ATTENTION = 'pill-yellow' (класс уже есть в components.css).
- `components/eval360/Report360View.tsx`: KIND_LABEL += ATTENTION «Зона внимания»;
  в PairFindings kinds = [CONSENSUS, ATTENTION, BLIND_SPOT, HIDDEN_POTENTIAL];
  заголовок группы: «Зона внимания (расхождение 0,4–0,5):». Порядок: консенсус →
  внимание → слепые → скрытый потенциал.
- Таблица SubjectPanel.tsx правок не требует — пилюля берётся из helpers по zone.

### 6. Процесс: `tasks/attention-zone/BRIEF.md` + `PLAN.md` по шаблонам.

## Проверка

1. Смоук zoneOfDelta: 0,3→CONSENSUS; 0,34→CONSENSUS (округление 0,3); 0,35→ATTENTION;
   ±0,5→ATTENTION; 0,55→BLIND_SPOT; −0,55→HIDDEN_POTENTIAL (симметрия!); ±0,6→BLIND/HIDDEN;
   null→null.
2. Смоук buildAnalytics на цифрах пары «подчинённые» Седлецкого: Проактивность (−0,5) и
   Решение проблем (+0,5) → ATTENTION; Командная (0,0), Ответственность (+0,2) → CONSENSUS;
   Лидерство (+0,67) → BLIND_SPOT; Гибкость (−1,17) → HIDDEN_POTENTIAL.
3. Смоук промпта: enum с ATTENTION в схеме, легенда категорий в system.
4. tsc оба пакета, next build.
5. Коммит в `mvp2`, пуш; записи в журналы. БД не меняется.
6. Приёмка пользователем: перегенерация Седлецкого — Проактивность и Решение проблем
   в блоке «Зона внимания», таблица результатов показывает жёлтую пилюлю «Внимание».

## Отвергнутые альтернативы

- Исключить 0,4–0,5 из разборов пар: теряется информация, против правила «все
  компетенции в парах».
- Делить консенсус только на фронтенде по Δ: kind в данных противоречил бы отчёту.
